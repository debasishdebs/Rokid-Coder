## 0. Surprises the planner must know first

1. **The Agents plugin is NOT a root Gradle module.** `settings.gradle.kts` includes `:plugin-lyrics ... :plugin-patcher` and no `:plugin-agents`. `plugins/agents/` is a standalone Gradle root (own `settings.gradle.kts`, `rootProject.name = "NexusAgentsPlugin"`) that points at `../../shared`, `../../bus-client`, `../../ink-engine`. `./gradlew :plugin-agents:testDebugUnitTest -PskipCxrGlobal=true` from the root fails: `project 'plugin-agents' not found in root project 'RokidNexus'`. The command that works is in §7.
2. **`../CxrGlobal` does not exist** (and `~/.m2/repository/com/example/cxrglobal` does not either). Only `:phone-hub` depends on `com.example.cxrglobal:lib:0.3.0` (`phone-hub/build.gradle.kts:59`). `:glasses-hub` does NOT (it uses `com.rokid.cxr:cxr-service-bridge:1.0-20260522.063600-105`, `glasses-hub/build.gradle.kts:51`), and it builds and tests fine here (§7). AGENTS.md's "the hubs link against it" is only true for the phone hub.
3. **No Compose anywhere in Nexus.** No `build.gradle.kts` in the repo mentions compose. Agents settings are plain `android.app.Activity` + programmatic Views via `NexusUi` (bus-client). The glasses side of a plugin cannot draw Compose at all: glasses UI is hub-rendered typed surfaces (`NexusCard`/`NexusReader`/`NexusNotice`). LiveFit/PCA Compose patterns apply to phone screens (new dependency work) and as visual language only on the glasses.
4. **Nexus is dark phosphor-green; LiveFit/PCA phone UI is light mint Material3.** Design §7 says reuse LiveFit/PCA Material components. That conflicts with the existing `NexusUi` dark look and with `Theme.Agents` (dark). Planner must rule which wins for Agents screens.
5. **TLS does not exist on either side yet.** agentd Task 11 (pinned TLS, `agentd/src/tls.ts`) is unwritten; agentd treats every phone link as untrusted, so all steering frames get `ack rejected error=monitor_only` until Plan 2's phone TLS server exists. Plan 1 doc says the phone is the TLS server for PhoneLink and agentd pins the phone cert TOFU (plan-1 Task 11, lines 572-596).
6. Agents' only HUD alert tier today is a notice with `interactive = true` and no `wakeDisplay`; the 90 s hold in the glasses hub keys on `interactive` (the flag), NOT on `actions` (see §4.2 trap).

### 2.2 Link topology (who is server, ports, handshake)
Two independent inbound paths exist, both feed the same `AgentSessionStore`:

A. **Daemon dials the phone (default, zero-setup)**: `AgentdLinkServer` (phone = TCP server, plaintext, newline-delimited JSON).
- `AgentdLinkServer.LINK_PORT = 8792`, `DISCOVERY_PORT = 8793` (lines 296-297), `RETRY_DELAY_MS = 2000`.
- `acceptLoop()` line 100: `ServerSocket(LINK_PORT)` (line 103) then `server.accept()` -> `LinkConnection(socket)` -> `serve()`. This is **the only ServerSocket in the Agents plugin and the place a TLS server would replace** (`SSLServerSocket`).
- UDP discovery: daemon broadcasts JSON `{"nexus":"agentd","v":1}` to `:8793` (checked in `isDaemonBeacon`, line 277); the phone unicast-replies `{"nexus":"agents-phone","v":1,"port":8792,"name":<Build.MODEL>}` (`replyTo`, line 284). `agentd/src/phone-link.ts` `DISCOVERY_PORT = 8793`, `PHONE_HELLO_TIMEOUT_MS = 15_000`.
- Handshake (agent -> phone first): `{"type":"hello","v":1,"machineId","machineName","token"}` (agentd `phone-link.ts:443`). Phone parses in `AgentdProtocolCodec.parse` `"hello"` branch (`AgentdProtocol.kt:81`): requires `v==1`, `machineId` (<=256), `token` (<=4096), `machineName` (<=160). Phone then `AgentdInboundGate` (line 317) -> `configStore.authorizeMachine(machineId, token, machineName)` -> `MachineTrustResult`: `TRUSTED`, `NEWLY_TRUSTED`, `REJECTED_BAD_TOKEN("bad_token")`, `REJECTED_NOT_INVITED("unknown_machine")` (`AgentsConfigStore.kt:75-100`). Reply `{"type":"hello_ack","v":1}` (`HELLO_ACK`, line 299) or `{"type":"hello_reject","v":1,"reason":...}` (`AgentdProtocolCodec.helloReject`, line 323). Trust rule: first machine ever = trust-on-first-use; others need the wearer-armed 2-min link window (`LINK_WINDOW_DURATION_MS = 2L*60*1000`, `AgentsConfigStore.kt:417`; `armLinkWindow()`); known machine + wrong token is refused and its token is never overwritten.
- After `hello_ack` agentd sends `snapshot` then deltas and `ping` every 30 s (`LINK_PING_INTERVAL_MS`); phone read timeout `LINK_IDLE_TIMEOUT_MS = 90_000` (`soTimeout`, line 372), max line `MAX_LINK_LINE_CHARS = 64 * 1024`, replies `pong {t}` (codec `"ping"` branch).
- Only the first accepted client is active (`activate()` closes the previous); on close, store sessions/approvals for providers `AGENTD_PROVIDERS = {CLAUDE, CODEX}` are cleared.
- **v2 is NOT negotiated.** hello is `v:1`; v2 frames (`alert`, `ack`, `session_upsert` with `v:2` fields, ...) simply start arriving. The current phone codec's `else -> AgentdAction.Ignore` silently ignores unknown types, so a v1 plugin tolerates a v2 agentd. Plan 2 needs to decide whether to add a capability signal in `hello_ack` (agentd currently sends none; `agentd/src/ws-server.ts:251` sends `hello_ack {v, server:{name,version,machineId,machineName}}`).

B. **Phone dials the daemon (pasted pairing / Tailscale)**: `AgentdClient` (OkHttp WebSocket, plaintext `ws://`).
- URL from `webSocketUrl(host, port)` (`WebSocketSupport.kt:129`): no scheme -> `ws://host:port`; explicit `ws://`/`wss://` kept. Daemon `ws-server.ts` listens on `:8792` (config `wsPort`), loopback hook server `:8791`.
- Handshake (phone first): `AgentdProtocolCodec.hello(token, versionName)` -> `{"type":"hello","v":1,"token":...,"client":{"name":"plugin-agents","version":...}}`; daemon -> `hello_ack` then snapshot. Close code **4401 = auth failed, non-retrying** (`BAD_TOKEN_CLOSE_CODE`, `AgentdClient.kt:273`); other closes retry with `ReconnectBackoff` (1/2/4/5 s jitter). Deadlines `DEADLINE_HELLO`, `DEADLINE_SNAPSHOT` = 15 s (`NETWORK_STEP_TIMEOUT_MS`).
- `AgentsMonitorService.reconcile()` (line 152): `agentdClient.start(config.agentd)` when a pairing slot exists; `linkServer.start()` (line 181) **only when agentd is enabled and NO pairing slot is configured** ("we simply listen: the daemon finds us"); otherwise `linkServer.stop`. So the two paths are mutually exclusive per phone config today.

Pairing format (parsed in `AgentdPairingParser.parse`, `AgentsConfigStore.kt:48`; produced by `agentd/src/pairing.ts:pairingPayload`): single JSON line
`{"v":1,"kind":"nexus-agentd","name":<machineName>,"host":<bestHostGuess>,"port":<wsPort>,"token":<token>}`. Validation: `v==1`, `kind=="nexus-agentd"`, host<=512 non-blank, port 1..65535, token<=4096, name<=160 (falls back to host). Stored as ONE slot (`agentd.host/port/token/name`, enabled flag `agentd.enabled`). Caller: `AddComputerActivity.kt:390/402`, saved at line 415 via `configStore.saveAgentd(config, enabled)`. **No `fp` (TLS fingerprint) field exists yet**; agentd plan-1 Task 11 adds `fp` to `pairingPayload`. The parser ignores unknown keys, so an added `fp` is backward compatible, but the plugin must be taught to read it. There is no QR scanner in the plugin (paste only); the design says "pairing QR": a QR flow is new work (no camera/zxing dependency today).

Outbound builders: `detail_open/close, fs_list, thread_start, approval_decision {v:1,requestId,decision allow|deny}, session_input, refresh, helloReject`.

- `/notice/closed`: `{noticeId, noticeInstanceId, noticeQuestionId, reason}` with `reason in user | timeout | owner | replaced | disconnect` (`NoticeCloseReason`, `shared/.../NoticeSurfaceContract.kt:11`; SDK enum `NexusNoticeCloseReason {USER, TIMEOUT, OWNER, REPLACED, DISCONNECT}`, `SurfaceModels.kt:690`). USER = BACK or double tap on the ring; TIMEOUT = ttl or 90 s absolute lifetime; OWNER = own `hideNotice()`; REPLACED = another plugin took the slot. A same-owner re-show does NOT emit REPLACED; SDK drops the old OWNER close after `hide` + `show` (`clearNoticeContext()`). Not delivered when the owner is what vanished. **`REPLACED` and `TIMEOUT` never mean "delivered"** (design §12.2).
- All three notice reply paths are owner-scoped direct replies: no receive prefix needed (`PathRules.isDirectReply/isOwnerScoped`, `shared/.../plugin/PathRules.kt:82-107`).
- One-answer rule: after the first confirm the band becomes inert; to ask again send a new `showNotice` or an `updateNotice` carrying `actions`/`interactive`; cosmetic countdown labels use `NexusNoticeUpdate(actions = labels, rearm = false)` (needs hub >= 1.4.11, `noticeInteractionVersion` 1 else `CAPABILITY_NOT_AVAILABLE`).
- Input claim (BUSSPEC "Input claim"): band with actions claims confirm; with 2+ actions it also claims forward/back (selection moves along the chip row, single page); with 0-1 actions swipes turn pages. BACK always dismisses and is never forwarded.
- TTL/lifetime: max 45 s TTL, **90 s absolute lifetime** from first accepted show (`MAX_LIFETIME_MS = 90_000L`). Reminder loops therefore must re-`showNotice`.
- Notice wake: `wakeDisplay = true` is honored only in `showNotice`; `/notice/update` with `wakeDisplay` or `backdrop` = `INVALID_NOTICE`.
