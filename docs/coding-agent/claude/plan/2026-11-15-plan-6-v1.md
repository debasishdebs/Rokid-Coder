**Goal:** Turn 0.8.0 into the 1.0.0 product.
- One phone app with Nexus embedded and the glasses app bundled inside it.
- Guided onboarding, with commit-then-reveal code pairing.
- macOS and Windows (WSL2) installers that check prerequisites first.
- The new repo layout, with an upstream-sync Action.
- Release CI, with publication blocked until the user's hardware matrix passes.

**Architecture:**
- **Upstream Rokid-Nexus is vendored under `vendor/nexus/` as a git subtree.**
  - Our Gradle build keeps upstream's module names (`:shared`, `:bus-client`, …) and only changes their `projectDir`, so upstream build files need no edits.
  - Upstream `phone-hub` is split, by one recorded patch, into a library `:phone-core` and the upstream app shell. Our `:mobile:app` depends only on `:phone-core`.
- **The phone app's Agents code** reaches the glasses through a private in-process `GlassesSurface` interface. An architecture task (T2) specifies it completely, from an inventory of every SDK interaction, before any code moves.
- **The computer side** is one npm workspace. It ships with a pinned Node runtime inside a macOS `.pkg` and a Windows `.exe` that installs a Linux bundle into WSL2.

**Tech Stack:** Kotlin (AGP 9.2, Compose Material3, JDK 17); Node 22 LTS + TypeScript (CommonJS) + node-pty; git subtree; GitHub Actions (macos-latest, ubuntu-latest, windows-latest with WSL, and an Android emulator job); pkgbuild/productbuild; NSIS.

### Task 6: SAS pairing as a full state machine on both transports (R1′) `[CR 2, CR 3]`

**Files:** see the ownership table: computer admission, CLI and rk prompts, the launcher hub, phone admission (`AgentdLinkServer`, `AgentdClient`, `AgentsConfigStore`), `SasPairing.kt`, `contracts/sas-vectors.json`.

**Interfaces:**
- **Attempt owner:** agentd's `PairingAttempt`, at most one at a time.
  - States: `IDLE → WINDOW_OPEN → PEER_TLS (fps fixed from the TLS handshake: canonical uppercase colon-hex SHA-256 of the DER) → COMMIT_SENT → NONCE_RECEIVED → REVEALED → AWAITING_CONFIRM → PINNED | ABORTED(reason)`
  - `reason`: one of `mismatch`, `cancel`, `timeout`, `disconnect`, `second_peer`, `second_commit`, `bad_reveal`.
- **Frames:** these are the only frames accepted before `PINNED`. They come in this order inside the TLS session, and anything out of order aborts.
  1. `sas_commit{v:2,c}`
  2. `sas_nonce{v:2,np}`
  3. `sas_reveal{v:2,nc}`
  4. `sas_confirm{v:2,ok}`, in both directions
- **Formulas:** as in R1′. `computeCommit` and `computeSas` in TS; `SasPairing.commit` and `SasPairing.code` in Kotlin.
- **Competing peers:** a second TLS peer while an attempt is past `WINDOW_OPEN` gives `ABORTED(second_peer)` for both, with the message `"More than one device answered — try again"`.
- **The QR/pairing-line fallback** `[CR 2]` supplies only the address and agentd's fp. It STILL runs the SAS. There is no bypass.
- **Confirmation IPC:** agentd → rk/CLI/installer over the 0600 launcher socket.
  - `pair_status{attempt, state, code?}` goes to every attached pairing client.
  - The client sends `pair_confirm{attempt, ok}`.
  - agentd accepts a confirm only for the CURRENT attempt id while in `AWAITING_CONFIRM`. Anything else is ignored and logged `[CR rev2-c]`.
  - `agentd pair` and the installer's pairing step are such clients.
- **Phone side:** the phone's onboarding or Add-a-computer screen shows the code and sends `sas_confirm`.
- **`pair-ready` announcement:** UDP `{"nexus":"agentd-pair-ready","v":1,"machineName","attempt":<random 64-bit>}`, carrying no secrets.
  - The phone accepts it only while onboarding PAIRING or Add-a-computer is open, and only once per attempt id.
  - At most one window per 30 s comes from announcements. Repeats are ignored.
