# Plan 3 live smoke results (Task 6)

Date: 2026-11-14. Branch `rokid-coder/plan-3`, base `aed0a190` (627/627 at base). Claude Code 2.1.285 on Haiku 4.5 (`--model haiku`, `/model` never typed), Codex CLI 0.169.0 (`-m gpt-6-luna`, no `-c`, no prompt sent).

## Setup and isolation

- agentd ran from `agentd/dist/cli.js run` with `NEXUS_AGENTD_STATE_DIR` and `rokidCoder.stateDir` pointing at temp dirs (`tailnetDiscovery=false`, Codex monitoring off). `rk` used the same dirs through `ROKID_RK_CONFIG_DIR`. `ROKID_CLAUDE_SESSIONS_DIR` pointed at the real `~/.claude/sessions`, read-only, because the real Claude writes its session file there. `~/.rokid-coder` was never created (checked at the end). Ports 8791, 8792 and the fake phone's 8793 were free before and after.
- Claude and Codex ran under `rk` in a pty (the Plan 1 `drv.py` Screen renderer plus a control file), in an already-trusted scratch directory. Claude loaded the plugin with `--plugin-dir plugins/claude-code`, so the hooks reached the temp agentd.
- The fake phone is the repo's `test/fake-phone.js` on the PhoneLink path over TLS: agentd dialled it, and pinned its certificate inside an `agentd phones allow-next` window. That is what "a pin present" means below, and a pinned TLS phone may steer. (Plan 1 used the WsHub path with the steer secret; the pinned path was not exercised there.) The driver sent `alert_shown` for every alert, as a real phone does.
- Session file watcher: polled `~/.claude/sessions/*.json` every 20 ms for files whose pid is below the `rk` process, and logged each change.
- Budget: Claude Haiku, three prompts in total (`say OK`, `Reply BANANA` sent by the phone, `Count from 1 to 300, one number per line, nothing else.`) plus one `/compact`. Codex: no prompt.

### 1. busy within 1.5 s: PASS
- Submit written at 158.838 (epoch s, last digits); Claude's file went `busy` with `statusUpdatedAt` 158.944, which is 106 ms later (the watcher saw it at 120 ms). The other submits gave the same: the third prompt 55 ms, the typed BANANA reply 145 ms after the phone's frame, the compact 99 ms after the command.
- Bumps of `statusUpdatedAt` while busy (R150): none. Each busy period was one write, then the idle write, over busy periods of 33.4 s (`say OK`, 3 s of work plus the 30 s Stop hold), 31.5 s (BANANA), 33.5 s (the 300-number stream, about 3 s of streaming plus the hold) and 12.3 s (compact). So a busy `statusUpdatedAt` is the time busy began and is never refreshed; any logic that treats an old busy stamp as stale would be wrong during a long turn. This was measured on turns with no tool calls; a long tool run was not measured.

### 2. paste plus `\r` as one write: PASS
- The driver wrote `\x1b[200~say OK\x1b[201~\r` with a single `write()` (logged as one send). The TUI showed `❯ say OK` submitted and answered `OK`; the text was not left sitting in the input box. The same held for the 300-number prompt.

### 3, 4, 5. `/model` checks: SKIPPED
- Reason: covered by the fake only (hard rule: never type `/model` into the user's real Claude, it rewrites `~/.claude/settings.json`). `~/.claude/settings.json` mtime is unchanged at the end of the smoke.

### 6. banner, no ghosting, bound state: PASS
- No phone paired: the banner (`Rokid-Coder launcher: attaching… …` and the `/rokid:status` line) and `No phone paired yet. Pair now? [Y/n]` were the first bytes of the run; Claude's first byte came 5.6 s later, after the answer. Claude then entered its alternate screen, so nothing of ours is drawn in or over the TUI. On exit the terminal-mode resets arrived in order (mouse, paste, cursor) and `rk` exited 0.
- Phone paired: the banner gained `On your glasses: open Agents to see this session.` and no prompt appeared. First TUI byte at +0.65 s, alternate screen at +0.81 s.
- **Bug found and fixed.** The first paired run bound (`launcher_bound` in the log), but the phone saw nothing: `/health` showed `sessions:0` and the first `session_upsert` arrived 184 ms after the first prompt. Claude's own `SessionStart` hook reaches agentd before the launcher's bind (the launcher polls every 500 ms), so it was dropped as unattached, and no later hook came until the first prompt. Fix: `LauncherHub` now has an `onBound` option, called after a successful bind with the session id, status and cwd (now read from Claude's session file); the daemon replays a `SessionStart` for an idle session. Regression test `bind_before_any_hook_shows_the_session_in_launcher_mode` (failed before the fix with `timed out waiting for an upsert at bind`, passes after) plus a `cwd` assertion in `reads_session_file_and_rejects_malformed`.
- Re-checked live after the fix, no prompt sent: about 1 s after `rk claude` started, the phone got `session_upsert mode=launcher status=idle capabilities={compact:true, model:true, followup:"ready"} cwd=<scratch dir>`.

### 7. model-invoked slash command and `UserPromptExpansion`: SKIPPED
- All four plugin commands (`on`, `off`, `status`, `pair`) carry `disable-model-invocation: true`, so the model cannot invoke them, and provoking another command would cost a prompt beyond the budget.

### 8. `rk codex` hint and the alternate screen: PASS, with a caveat
- Plain `rk codex -m gpt-6-luna` in a pty: the three-line hint was the first output, at +0.00 s. Codex began its own output at +0.17 s and entered the alternate screen (`?1049h`) at +0.43 s, then cleared only that screen. On exit it left the alternate screen (`?1049l`), which puts the normal screen back with the hint intact. The agentd-up variant has no `agentd isn't running` line (agentd was up and paired, so no pairing prompt either).
- Caveat: the hint is readable for about 0.4 s before Codex covers it, and again after Codex exits; it is not visible while Codex runs. It is not wiped.
- Quit without a prompt: the first Ctrl-C ended Codex at once (`Disconnected from this task… codex resume <id>`); `rk` exited and no child was left. `~/.codex/config.toml` mtime changed during the run (Codex's own start-up bookkeeping, as seen in Plan 1); `rk` and agentd never write there.
- Path B / the plugin attach (`rokid:on` inside Codex): SKIPPED, the Codex plugin is not installed (R25). It goes on the morning list.

### 9. compact: PASS
- The phone sent `launcher_command compact` while the session file read idle (after the Stop wait of the previous turn had expired). Claude's file went busy 99 ms later; the TUI showed `❯ /compact` then `Compacted`, with both `PreCompact` and `PostCompact` plugin hooks listed as `completed successfully`. `ack applied` reached the phone 12.4 s after the command, 18 ms before the session file returned to idle: it was sent after the PostCompact, not at once.

### 10. late reply: PASS
- `settings_sync` with `waitLimitMs=30000` returned `ack applied`. After `say OK` the phone got `alert kind=done` and `capabilities.followup="waiting"`; 30 s later `followup_closed reason=timeout` and `alert_closed reason=expired`, then `followup` went `unavailable` and then `ready`.
- First `followup` attempt was `rejected bad_session_key`: my driver took the key from the wrong field. It consumed nothing. The second, `followup claude:<id> "Reply BANANA"`, returned `ack applied` after 99 ms. The TUI showed `❯ Reply BANANA` as an ordinary typed prompt and Claude answered `BANANA`; there was no `Stop hook error: Follow-up from Rokid glasses` line, which is what a hook delivery looks like (Plan 1 smoke). The phone then got `alert kind=done body=BANANA`.

## Other observations (not fixed)
- The phone gets runs of identical `session_upsert` frames (6 in a row about 3 s into the first turn, 3 around the Stop). Harmless; the Plan 1 coalescing note still stands.
- After `/exit` the temp `attached.json` still lists the exited launcher session (mode `launcher`). It is harmless for a dead session, but the file grows by one entry per `rk claude` run; not checked whether anything prunes it.
- During the Stop hold (30 s) Claude's own status stays `busy`; commands wait for it, as designed.
